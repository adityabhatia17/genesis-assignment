# Peer review — `docs/ARCHITECTURE.md` (initial "locked" draft)

**Date:** 2026-09-26
**Reviewer stance:** a principal engineer reading the draft cold, with the assignment PDF open, checking every claim against the platforms' current documentation.
**Verdict:** **Approve the direction, block the details.** The draft's architecture is the right shape and several decisions are genuinely good. But it contains security contradictions, platform facts that are wrong or out of date, requirement gaps, and correctness bugs in its reference code — enough that "implement exactly this" would fail the assignment in visible ways. Every finding below has a concrete correction that the rest of this doc suite implements.

> Severity: **Critical** = fails a stated requirement or opens a real security hole; **High** = likely user-visible failure or major rework; **Medium** = correctness/maintainability debt a reviewer would flag; **Low** = polish.

---

## 1. What the draft gets right (keep)

1. **"The LLM is an untrusted code producer"** as the organizing principle, with explicit, non-negotiable trust boundaries (§1–2).
2. **No generic proxy** — HighLevel reachable only through explicit, allow-listed routes (decision 13).
3. **Path-based tenancy** `users/{uid}/projects/…` with rules scoped by path (decision 7).
4. **One cursor contract** hiding HighLevel's three pagination styles (decision 12).
5. **Location-level install**, one user ↔ one location (decision 1) — matches the assignment exactly.
6. **`fetch()` + SSE straight to the function URL**, because `EventSource` can't POST or send `Authorization`, and Hosting rewrites buffer streams (decision 4).
7. **`srcdoc` iframe with `sandbox="allow-scripts"` and never `allow-same-origin`** (decision 5).
8. **Marker-delimited text protocol** instead of JSON tool calls, for live streaming (decision 3).
9. **One provider behind a thin interface** (decision 16), **Firestore-only storage** (decision 24), **one Firebase project + emulators** (decision 9).
10. **Idempotency key per submit**, pre-written README decisions, a timed Loom script, a bonus priority list and a "what we are not building" list — good delivery discipline.

### 2.1 Security

| F01 | **Critical** | §10 last paragraph | The preview receives the user's **Firebase ID token** via a `postMessage` handshake and uses it to call the proxy. The sandbox blocks cookies/storage but **not network**: generated code (or HighLevel data it renders) can send the token anywhere (`fetch`, `new Image().src`, CSS `url()`). With it, anyone can call Firestore's REST API as the user (read/write every project, file and message the rules allow) and the HighLevel proxy for ~1 hour. This directly contradicts §1 ("never holds … a credential") and §23's own DoD check | **Host bridge**: the iframe gets a `MessagePort`, not a token. A **CSP meta tag** (`connect-src 'none'`, `img-src data: blob:` …) removes all network egress from generated code. The parent validates each call against the runtime manifest and makes the authenticated request. (`04-high-level-design.md` Q1–Q2, `06` §13) |
| F02 | High         | §10                | Direct `fetch` from a sandboxed (opaque-origin) document sends `Origin: null`; the proxy would need `Access-Control-Allow-Origin: *` or `null`, weakening CORS for every route                                                                                                                                                                                                                                                                                                                                                                  | Fixed by F01: only the SPA origin calls the backend; CORS allow-list is exact origins                                                                                                                                                                                                                                          |

### 2.4 Reliability and correctness

| ID  | Sev          | Where                        | Finding                                                                                                                                                                                                                                                                                                                                                                                                                       | Correction                                                                                                                                                                                                                             |
| --- | ------------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F31 | **Critical** | §9.3                         | `refreshUnderLock` calls HighLevel **inside** a Firestore transaction callback.
